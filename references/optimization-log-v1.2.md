## 重构方法（可复用）

2. 合并同类：踩坑记录×3 → 1份24条表；工作流×3 → 创作流程1份；知识库清单×2 → 1份

## 自检脚本开发模式（scripts/quality_check.py）

1. **先读真实产物格式再写解析器**——demo/第X集_完整版.md 的碎片表格式：
   `| A1 | A | 00:00→00:03 | ECU·固定 | 画面描述 | 🔊耳光声💓无🫧泛红 | **P0** [风格锚点] ... |`
2. 用全部6集真实 Demo 验证（不是造样例）——第3集14/14全过，第4-6集自动抓到"碎片平均7.6-7.8秒偏长"，与踩坑记录记载的真实问题吻合
3. 修过的 bug（同类脚本会再遇到）：
   - 正则字符类混中英文引号 `[“"]` 直接 SyntaxError——需转义 `[“\"]`
   - 检查函数签名不同（text / frags / text+frags）——用 dispatch dict 分发，不要统一传参
   - 声音匹配跨场景误报：全文匹配"清晨+烛火"会误伤不同场景的行 → **改行级检测**，跨行组合降级为🟡人工确认
   - 标题关键词提取：长句连续CJK匹配不到正文 → 用 2-3 字滑窗去重 + 虚词过滤

## git 合并远端冲突处理

- 本地重构后 push 被拒（远端有未拉取的 v1.1.0 提交，含 Blocking 场景布局——本地版没有）
- 处理链：fetch → 看远端提交内容 → **abort rebase** → 从 origin/main 提取有效段落 → 手动合并进重构版（记忆文件表+记忆工作流+阶段一+Step4同步共4处）→ merge origin/main → 冲突用 `--ours` 解决（本地版已含全部有效内容）→ push
- 教训：**重构前先 fetch 检查远端是否有未拉取提交**，避免重构完才发现要合并新内容

## 迭代惯例（v1.3+ 遵守）
